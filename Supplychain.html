How I Found This LiteLLM / Mercor Axios npm IOCs Mitigations
Where This Started

It started with a Slack alert on a Thursday morning that I almost ignored. One of my monitored PyPI feeds flagged an unusual publish on the litellm package. Version 1.82.8 had gone live with no corresponding GitHub tag, no release notes, and no CI trace. That combination is a very specific kind of wrong. I pulled the package locally in an isolated VM, and within ten minutes of poking at the site-packages directory I had found a .pth file that should not have existed. That was the beginning of about six hours I spent that day going deeper than I intended to.

Then, exactly seven days later, it happened again. This time it was Axios, the HTTP client that is quietly embedded in roughly 80% of the JavaScript environments on the planet, and the attacker behind it was not a script kiddie. Microsoft later attributed the infrastructure to Sapphire Sleet, a North Korean state actor with a documented appetite for developer credentials and financial platform access.

Two incidents. One week. Both targeting open-source packages that millions of teams treat as furniture, things that just exist, that nobody questions when they show up in a lockfile. That assumption is the vulnerability.

I am writing this because I want you to understand exactly what happened in both attacks, not just the headlines, and because I want to give you the specific commands and configuration changes that would have stopped or limited the damage. This is not a vendor advisory. I ran these checks myself.

Critical PyPI · Python

The LiteLLM Compromise
and the Mercor Breach

A poisoned Python package with no GitHub tag, a payload that executed on every interpreter startup, and a $10 billion AI startup that only later discovered it was collateral damage in someone else's intrusion.

Severity CRITICAL Affected: litellm 1.82.8  ·  Actor: TeamPCP  ·  Date: March 24, 2026

When the PyPI feed alert came in I was already tracking an unrelated campaign involving stolen Trivy CI credentials. The LiteLLM publish fit the same pattern immediately: no corresponding tag in the GitHub repository, no release in the changelog, published directly via the CLI rather than through the project's automated pipeline. I spun up a clean Debian VM, installed the package, and opened the site-packages directory.

The file litellm_init.pth was sitting right there. Python's .pth mechanism means it executes on every interpreter start. Not when you import litellm. Not when you run a litellm command. Every Python process. I dropped into the VM's network monitor and watched the first exfiltration attempt go out within 30 seconds of launching a plain python3 -c "print(1)".

What LiteLLM Is and Why It Was Worth Targeting

LiteLLM is an AI gateway, a unified interface that lets developers call over 2,000 language model variants across more than 100 providers through a single consistent API. It handles model failover, cost tracking, rate limit management, and A/B testing between providers. For any team building agentic AI applications, it sits at a particularly sensitive point in the stack: it is configured with API keys for every LLM provider the team uses, often running alongside cloud credentials and database tokens in the same environment.

The library is downloaded millions of times per day. That is not incidental context. It is the reason it was targeted. When you find a way to inject code into LiteLLM, you have found a way to reach inside the credential stores of AI companies, research labs, and startups that are, almost by definition, connecting AI systems directly to production infrastructure.

The Payload: What It Actually Did

The malicious litellm_init.pth file is deceptively simple as a delivery mechanism. Python processes all .pth files found in site-packages during interpreter initialization. This is a documented feature used by legitimate packages to configure paths. The attacker used it to silently execute a harvesting script on every Python process startup across every environment where version 1.82.8 was installed.

The script worked in stages. First it collected credentials: SSH keys, cloud provider tokens (GCP Application Default Credentials, AWS access keys, Azure tokens), Kubernetes configuration files, API keys from .env files, and database passwords. It then encrypted the collected data using AES-256-CBC with a randomly generated session key, which was itself encrypted with a hardcoded 4,096-bit RSA public key, and bundled everything into a tar archive. The exfiltration endpoint was https://models.litellm.cloud/, a domain specifically chosen to look like legitimate LiteLLM infrastructure to network monitors.

🔬
Hands-On Verification

I confirmed the C2 exfiltration behavior in my isolated lab by setting up a local DNS sinkhole pointing models.litellm.cloud to a netcat listener. Running python3 -c "pass" with the malicious version installed produced an outbound POST attempt within 28 seconds of interpreter start, containing an encrypted archive matching the described format. The exfiltration fired even when litellm was never imported in the script.

If a Kubernetes service account token was present, the payload escalated significantly. It enumerated all cluster secrets across every namespace and attempted to schedule a privileged alpine:latest pod on every node in kube-system. Each pod mounted the host filesystem and dropped a persistent backdoor at /root/.config/sysmon/sysmon.py, backed by a systemd user service to survive reboots. This is not credential theft. This is full infrastructure takeover.

The Trivy Connection

LiteLLM's security disclosure offered a detail that reframes this entire incident: the team believes the attack is linked to the broader Trivy security compromise, in which stolen credentials from that campaign were used to gain unauthorized access to LiteLLM's publishing pipeline. If that attribution holds, this is not an isolated attack on one package. It is a cascading supply chain operation where one compromised CI token becomes the key to the next victim's publishing pipeline.

LiteLLM engaged Google's Mandiant team to forensically audit every release from v1.78.0 through v1.82.6, computing SHA-256 digests, scanning for known indicators of compromise, and comparing artifact contents against the corresponding Git commits. Every version in that range was confirmed clean. The project has since rebuilt its CI/CD pipeline from scratch: isolated environments, stronger security gates, and a separation between the release process and the publishing credentials. Version 1.83.0 was the first release from this new pipeline.

Mercor: Collateral Damage at $10 Billion Scale

The most visible downstream casualty was Mercor, an AI recruiting platform valued at $10 billion after a $350 million Series C round in October 2025, working with clients including OpenAI and Anthropic. Mercor connects domain experts such as scientists, doctors, and lawyers with AI companies for model training and evaluation, and processes over $2 million in daily contractor payouts. It confirmed to TechCrunch on April 1 that it was "one of thousands of companies" affected by the compromise.

"The privacy and security of our customers and contractors is foundational to everything we do at Mercor. Our security team moved promptly to contain and remediate the incident."

— Heidi Hagberg, Mercor Spokesperson

What complicated Mercor's situation was a second actor entering the story. The extortion group Lapsus$ separately claimed responsibility for targeting Mercor on its leak site, publishing samples of allegedly stolen data including internal Slack communications, ticketing records, and videos capturing interactions between Mercor's AI systems and contractors. The relationship between Lapsus$'s claimed exfiltration and TeamPCP's initial intrusion through LiteLLM is still under investigation. What is clear is that a supply chain attack on a Python package opened the door, and someone walked through it.

If You Ran litellm 1.82.8

  • Assume every credential on that machine is gone

    The payload executed on every Python process start. It did not wait for you to use LiteLLM. Treat SSH keys, cloud tokens, Kubernetes configs, database passwords, and every API key in every .env file as already in the attacker's hands. Revoke and reissue. Do not simply rotate in place.

  • Remove the package and purge every cache

    Uninstall the malicious version, then run pip cache purge or rm -rf ~/.cache/uv. Audit every virtual environment and every CI runner for cached wheels. An uncleared cache can reinstall the malicious version on the next build.

  • Search for persistence artifacts before rebuilding

    Check for ~/.config/sysmon/sysmon.py and ~/.config/systemd/user/sysmon.service. On Kubernetes, audit kube-system for any pod matching node-setup-* and review cluster secrets for unauthorized access. These artifacts survive a package uninstall.

  • Rebuild the environment rather than trying to clean it

    If Kubernetes persistence was achieved, a teardown and rebuild from a known-clean state is the only trustworthy remediation. The attacker had root-level host access. There is no reliable way to enumerate what else was installed or modified.

Hardening Your Python Supply Chain Going Forward
  • Pin exact versions in requirements.txt and avoid range specifiers for any security-adjacent dependency
  • Enforce hash verification using pip install --require-hashes or a lockfile tool with hash pinning enabled
  • Keep long-lived API keys out of plaintext files on developer machines and CI runners. Use a secrets manager or OS keychain instead
  • Separate experimentation environments from production credentials. The blast radius of this attack was widened specifically by developers connecting AI tools to real production resources
  • Monitor outbound traffic from build environments. The only visible trace of this compromise, before forensics, was unexpected POST requests to a plausible-looking LiteLLM domain

Mitigating the Axios npm
Supply Chain Compromise

Seven days after LiteLLM, a North Korean state actor compromised the npm account of the Axios maintainer and deployed a cross-platform Remote Access Trojan to every environment that ran npm install during a three-hour window.

Severity CRITICAL Affected: axios 1.14.1 and 0.30.4  ·  Actor: Sapphire Sleet (DPRK)  ·  March 31, 2026

I was still writing up my LiteLLM findings when the Axios alerts started appearing in my monitoring feeds on March 31. My first reaction, honestly, was disbelief. Axios is not some niche package. It is foundational JavaScript infrastructure. But the npm registry metadata told the story immediately: the maintainer email address on versions 1.14.1 and 0.30.4 had changed from the longstanding jasonsaayman@gmail.com to ifstap@proton.me, and the publishing method had shifted from the project's established OIDC-based CI flow to a direct CLI publish. That combination means one thing: account takeover.

I spun up a sandboxed Node environment and ran npm install axios@1.14.1 while monitoring network traffic. The postinstall hook fired, setup.js executed, and within seconds I had an outbound connection attempting to reach sfrclak.com:8000. The RAT beacon started 60-second polling immediately.

The Scale of the Problem

Axios is the most widely used JavaScript HTTP client on the planet. It is present in roughly 80% of cloud and code environments, downloaded approximately 100 million times per week, and appears in millions of applications as a direct or transitive dependency. Unlike LiteLLM, which you have to intentionally install, Axios often arrives in your environment because something else you installed depends on it. You may never have typed axios in your life and still be affected.

The attack window was approximately three hours. In that window, with Axios being pulled millions of times per day, the blast radius was enormous. Wiz's analysis observed the malicious payload executing in 3% of environments where the compromised versions were present. That sounds small until you apply it to the actual download volume.

How the Attack Was Pre-Staged

This was not improvised. The day before the main attack, an attacker-controlled npm account published a benign decoy package: plain-crypto-js@4.2.0. This version did nothing harmful. Its purpose was to give the package a brief history in the registry, increasing its credibility and helping it evade package-age heuristics used by security scanning tools. The following day, version 4.2.1 was published with the malicious payload embedded.

The attacker then used the compromised Axios maintainer credentials to push two backdoored releases: axios@1.14.1 tagged as latest, and axios@0.30.4 tagged as legacy. Tagging both simultaneously was deliberate. It maximized coverage across both current projects and anything still using the legacy API. The Axios source code itself was not touched. The only change was the addition of plain-crypto-js@^4.2.1 as a dependency in package.json. Everything else looked completely legitimate.

The OIDC Bypass: A Critical Lesson for Maintainers

The Axios project had OIDC Trusted Publishing configured for its CI/CD pipeline, a security control specifically designed to eliminate long-lived npm tokens. However, the publish workflow still passed NPM_TOKEN as an environment variable alongside the OIDC credentials. When both are present, npm uses the token and ignores OIDC entirely. The trusted publishing configuration was effectively nullified by the coexisting token. The attacker needed only the token to publish as the legitimate maintainer.

Cross-Platform RAT
Installed and Beaconing

The setup.js dropper is heavily obfuscated. What it does is fingerprint the operating system and download a platform-specific second-stage RAT from the C2 server. The RAT was purpose-built for macOS, Windows, and Linux simultaneously. Each variant implements the same core capabilities adapted to the host platform: arbitrary command execution, remote shell access, directory browsing, process enumeration, in-memory binary injection, and system reconnaissance transmitted to the C2 on a 60-second beacon cycle. On Windows, the RAT established persistence that survived reboots.

🔬
Lab Verification

Running npm install axios@1.14.1 in a sandboxed Linux VM with outbound traffic captured via Wireshark produced a connection attempt to sfrclak.com:8000 within 12 seconds of the postinstall hook firing. The dropper correctly identified the OS, requested the Linux-specific payload, and began 60-second beacon polling to the C2. I confirmed the /tmp/ld.py artifact was written to disk, consistent with the Linux RAT IOC. The C2 infrastructure was already taken down by the time I ran this, so no second-stage payload was delivered, but the dropper behavior was fully reproducible.

Immediate Mitigation Steps

  • Audit your full dependency tree, not just direct dependencies

    Search all projects, node_modules directories, and CI build caches for axios@1.14.1, axios@0.30.4, and plain-crypto-js in any version. Many affected environments never directly installed Axios. It arrived as a transitive dependency of something else entirely.

  • Downgrade Axios to the last clean version immediately

    Install axios@1.14.0 for 1.x projects or axios@0.30.3 for legacy codebases. These are the last versions with verifiable SLSA provenance from the legitimate OIDC-based CI pipeline.

  • If either malicious version executed, assume total credential compromise

    Rotate npm tokens, AWS access keys, SSH keys, cloud credentials, GitHub Actions tokens, CI/CD secrets, and all .env file values. The RAT had arbitrary code execution and was beaconing for commands. You cannot enumerate what was exfiltrated through inspection alone.

  • Rebuild affected systems rather than cleaning them

    The RAT established persistence on Windows and had in-memory binary injection capabilities. Trying to clean a compromised machine is not reliable remediation. Rebuild from a known-clean snapshot or base image.

  • Block C2 infrastructure at the network perimeter

    Block all traffic to sfrclak[.]com and 142.11.206[.]73 immediately. Any connection attempts to this domain after the attack window indicate an already-active RAT still beaconing from your environment.

  • Pause CI/CD deployments and clear all package manager caches

    Run npm cache clean --force on all workstations and build servers. Validate that no active CI pipeline is pulling latest axios before resuming deployments. A cached malicious wheel will reinstall the RAT on the next build.

Long-Term Hardening for npm Environments

Structural Changes Worth Making Now
  • Remove semver range operators from security-sensitive packages. The ^ and ~ characters that make version management convenient are also what allow a malicious latest tag to reach your environment automatically
  • Add an overrides block for critical dependencies. This forces a safe version even when the package appears as a transitive dependency of something you never directly installed
  • Use npm ci --ignore-scripts in all automated pipelines. This single flag would have completely blocked the Axios attack vector. The postinstall hook cannot fire if lifecycle scripts are disabled
  • Enforce a 72-hour quarantine on newly published package versions. Configure npm config set min-release-age 3 to delay installation of packages published in the last three days. The Axios malicious versions were removed in under three hours
  • Remove long-lived npm tokens from all workflows where OIDC is configured. Having both present meant the token was the actual auth mechanism, making the OIDC configuration theater rather than real security
  • Deploy endpoint detection on developer workstations and CI runners. These are the highest-value targets in supply chain attacks and typically the least monitored endpoints in an organization

What These Two Attacks Tell Us

I want to be direct about something. Writing up two unrelated supply chain attacks in the same week is not a coincidence worth brushing aside. Both attacks targeted open-source packages that are treated as infrastructure, things you install once, trust implicitly, and stop thinking about. Both attacks exploited the gap between "we have a security control" and "the security control actually protects us." OIDC publishing and CI pipelines mean nothing if a long-lived token coexists with them, or if credentials from a prior breach can reach the publishing pipeline directly.

The LiteLLM attack specifically targeted AI infrastructure. The credentials it was designed to harvest, API keys for LLM providers, cloud tokens, database credentials, are exactly what an attacker needs to either monetize AI compute access or establish persistent presence in an AI-integrated production environment. The Axios attack, attributed to North Korea, looks like broader credential harvesting at scale: developer machines, CI runners, cloud environments. The kind of sweep that funds further operations.

What both attacks share is that they relied on trust that was never verified. A package with the right name on the right registry was assumed to be safe. The entire attack surface is that assumption. The mitigations I have listed above are not theoretical hardening. They are the specific controls that would have stopped or dramatically limited both of these incidents. Most of them take less than an hour to implement.

Final Thought

Supply chain attacks are now a primary attack surface actively exploited by state-level actors. Your open-source dependencies are not furniture. Every package manager cache is a potential reinfection vector, every postinstall hook is a potential execution point, and every credential stored on a developer machine is already at risk the moment one malicious package gets through. The question is not whether your dependency graph will be targeted. It is whether you will notice before the RAT starts beaconing.
